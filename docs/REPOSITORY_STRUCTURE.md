# Repository Structure

This repository uses a deterministic materialization architecture rather than a conventional `src/` + package-bundler layout.

## Canonical top-level ownership

- `.bootstrap/` — compressed/bootstrap source payload consumed only by `scripts/materialize.py`.
- `.github/workflows/` — CI gates, materialization certification, and GitHub Pages publication for `dev`.
- `assets/` — canonical brand assets that are safe to keep as repository source.
- `docs/` — architecture and ownership documentation only.
- `mockups/` — optional mock-mode fixtures and adapters; never production records.
- `scripts/` — canonical materializers, domain cores, browser adapters, CSS fragments, certification scripts, and tests.
- `README.md` — operational rules and high-level ownership map.

## Generated root files

Files such as `index.html`, `app.js`, and materialized CSS are generated by `python scripts/materialize.py` from `.bootstrap/` plus `scripts/`. They are intentionally not required to exist in the clean repository tree before materialization.

Do not move materializer source into generated output folders and do not commit `_site/`.

## Structural rules

1. Development is performed only on `dev` unless explicitly authorized otherwise.
2. `main` remains untouched.
3. Domain ownership stays explicit: one canonical owner per global surface or domain.
4. Cross-cutting passes must not silently take ownership from domain materializers.
5. CI must materialize from a clean checkout before validating generated output.
6. GitHub Pages publishes only the certified `_site` artifact, excluding `.git`, `.github`, `.bootstrap`, `_site`, and `scripts`.
7. Temporary one-shot mutation workflows must be removed after their job is complete.
8. Python caches, local test output, browser screenshots, and other execution artifacts must never become repository source.

## Adding or changing a module

Prefer this sequence:

1. Add/update the domain core or canonical source under `scripts/`.
2. Add/update the browser/UI adapter and scoped CSS under `scripts/`.
3. Keep a single materializer entry point for the domain.
4. Wire the materializer into `scripts/materialize.py` in dependency order.
5. Add source and materialized tests.
6. Extend the Pages certification workflow only when the new domain requires a new invariant.
7. Verify that a second materialization is idempotent.

This structure is intentionally conservative because the project relies on deterministic reconstruction and artifact certification.
